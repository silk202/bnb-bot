# FlashBolt Solana program — configuration, authority and admin handshake (2026-11-21)

Milestone 1 of the on-chain program described in the V3 review, plus its first
security follow-up. This build replaces the previous starter functionality (the
Anchor Counter) with the configuration registry and authority controls. It
contains **no** trading surface: no counter, no swap CPI, no flash loan and no
execution instruction.

The Config PDA is derived from `[b"flashbolt_config"]` and stores exactly the
registry the V3 review asked for:

| Field | Purpose |
| --- | --- |
| `admin` | configuration, authority management, admin handover, unpause |
| `executor` | authorized signer for arbitrage execution |
| `pause_authority` | may activate the emergency pause, never lift it |
| `pending_admin` | nomination awaiting acceptance (`default` = none in flight) |
| `paused` | blocks execution while true |
| `bump` | PDA derivation bump |
| `version` | configuration schema version (currently `1`) |

Account size is `CONFIG_ACCOUNT_SPACE = 139` bytes (8-byte discriminator +
4 × 32-byte keys + bool + bump + version); a test asserts the on-chain size does
not drift. The program has never been deployed, so the schema still grows in
place at version `1` — the version field exists to make the first real migration
explicit rather than silent.

## Instruction surface

| Instruction | Signer | Rules |
| --- | --- | --- |
| `initialize_config(executor, pause_authority)` | initial admin | creates the PDA; the admin becomes `admin`; all three authorities must be non-default and distinct |
| `update_authorities(executor?, pause_authority?)` | admin | role checked **before** the arguments; at least one change; result must still have three distinct keys; admin is **not** transferable here |
| `propose_admin(new_admin)` | admin | nominee must be non-default and distinct from the current admin, executor and pause authority; replaces any earlier nomination |
| `accept_admin()` | nominated key | must match `pending_admin`; becomes `admin`; nomination cleared |
| `pause_program()` | pause authority **or** admin | refuses when already paused |
| `unpause_program()` | admin only | refuses when not paused |

Asymmetry is deliberate: pausing must be easy and immediate, lifting a pause
must require the administrator, so a compromised pause key cannot re-enable
execution.

### Why the admin handshake is two steps

`update_authorities` cannot move the admin key, and `accept_admin` completes a
transfer only when the nominated key signs. A one-call admin transfer can brick
the registry by pointing at a typo, a burn address or a key the operator does
not control; the handshake makes the mistake recoverable — the admin simply
proposes a different key, because a new proposal overwrites the pending one.

Distinctness is checked twice: at proposal, and again at acceptance against the
live config. The executor or pause authority may rotate onto the nominee while
the handshake waits, and the tests cover exactly that case.

`Config::execution_allowed(executor)` encodes the predicate a later execution
instruction must apply — `!paused && version == CONFIG_VERSION && executor ==
signer`. **Nothing enforces it on chain yet** because no execution instruction
exists in this build; that is the honest boundary of Milestone 1.

## What is deliberately absent

- DEX CPI interfaces, venue allowlists and account metas.
- Flash-loan borrow/repay logic — not every DEX supports flash loans, and a
  placeholder CPI would be worse than none.
- `flash_arb`, token validation, repayment/profit enforcement, execution events.
- Any mainnet program entry: `Anchor.toml` has `localnet` and `devnet` only,
  and the preflight refuses READY if a `[programs.mainnet]` entry appears.

These stay blocked until the provider instruction interfaces are real, exactly
as the review required.

## Preflight gates

`scripts/solana-program-preflight.sh` is read-only and prints every blocker.
It exits non-zero (BLOCKED) on any of:

- `declare_id!` still being the Anchor template placeholder;
- `declare_id!` differing from the confirmed address;
- any `Anchor.toml` program entry differing from it, or a mainnet entry;
- the program keypair (build output, then the retained keypair) deriving an
  address other than the confirmed one;
- a missing IDL, or an IDL whose `address` differs from the confirmed one;
- a missing toolchain, no devnet deployer, or a mainnet-configured CLI.

that loader with `Instruction(InvalidAccountData)`. The program itself is
unaffected.

Deploy only to devnet, and only with explicit approval:

```bash
solana config set --url https://api.devnet.solana.com
solana program deploy \
  --program-id solana/target/deploy/flashbolt_solana-keypair.json \
  solana/target/deploy/flashbolt_solana.so
```

The LiteSVM tests load `target/deploy/flashbolt_solana.so` and fail with the
build command when it is missing — they do not silently skip.

## Unpause precedence

`unpause_program` checks, in order: (1) the signer is `config.admin`, else
`UnauthorizedAdmin` (6000); (2) `config.paused`, else `ProgramNotPaused`
(6003). Then it clears the flag and emits `ProgramUnpaused`.

| Caller | Pause state | Result |
| --- | --- | --- |
| pause authority | paused | 6000 — the role wins over the state; the pause key may never lift a pause |
| former admin, after a handover | paused | 6000 — the authority is read from the live config, so the old key is powerless the moment `accept_admin` lands |
| pending admin, handshake in flight | paused | 6000 — a nomination is not a role |
| stranger | paused or not | 6000 — the same refusal either way, so the error reveals nothing about the pause |
| admin | not paused | 6003 — authorized, so it gets the state error |
| admin | paused | success — `ProgramUnpaused { admin }` |

Two things unpause deliberately does not do. It does **not** clear
`pending_admin`: a handshake survives an emergency stop, and only the nominee
can complete it. And it does **not** check `version`: `execution_allowed`
already refuses to authorise execution on a schema this build does not know, so
lifting a pause enables nothing — while a version gate here could leave a paused
account unrecoverable after a bad migration. `pause` is version-agnostic for the
mirror-image reason: an emergency stop must work even on an unrecognised schema.

## Next milestone — still blocked on the provider choice

The first thing the provider choice decides is the instruction shape, because
the two shapes on Solana today are not interchangeable:

- **A lender whose borrow/repay can be CPI'd** from our program, so `flash_arb`
  brackets the swap and asserts repayment itself.
- **A lender that only supports top-level bracketing.** Kamino's SDK builds a
  `flashBorrow`/`flashRepay` pair around a `borrowIxIndex` the lender checks, and
  marginfi's `lending_account_start_flashloan`/`end_flashloan` pair enforces its
  health check at the recorded end index and — per its own docs — **cannot be
  called through CPI**. There the borrow and repay are separate top-level
  instructions with our program between them, so `flash_arb` must verify the
  repayment obligation it is handed instead of assuming the lender enforces it.
- **The DEX.** Jupiter's Router (`/build`) returns raw Metis-routed instructions
  for CPI and custom flows with no swap fee, but they arrive from an off-chain
  quote. A program executing them must still pin every account, bound slippage
  on chain and refuse a route that does not start and end with the expected
  mints. Direct pool CPIs (Raydium, Orca Whirlpool) drop the off-chain step but
  fix the venue.

Non-negotiables for either choice, before any code: nothing the instruction
receives — repaid amount, route, pool list, minimum out — may be trusted from
the client; it is re-derived or bounded on chain from pool state. Profit is
measured from token-account balances before and after, never from a claimed
number. Mints with a transfer fee, permanent delegate, transfer hook or freeze
authority are refused unless explicitly allowlisted, because fee-on-transfer
breaks repayment arithmetic. Program IDs are constants, checked on every CPI
account, and `invoke_signed` is used for nothing but our own PDA.

Decision needed: one lender plus one DEX (or one aggregator), and whether the
first deployment is devnet-only.
